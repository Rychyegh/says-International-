Independent PV frontend integration — 3 October 2026

The supplied backend contract in independent-pv-backend-contract.txt supersedes the previous provisional camelCase request contract. Do not implement the old request fields.

Implemented:
- Item creation preserves per-item provider IDs; multi-provider headers carry null payee_id and "Multiple providers".
- Multi-item review uses pre-audit then item /authorize, separate from payment, with voucher version and a durable Idempotency-Key for each item decision. Aggregate /approve is not used for multi-item vouchers.
- Payment account dropdowns read GET /finance/payment-accounts. No account ID is inferred from a name or legacy expense code. The adapter accepts an accounts array with id/is_active/account_type (asset or expense), or source_accounts/expense_accounts arrays with id/is_active. If the backend publishes a different envelope, align this adapter before enabling payments.
- The disbursement body is source_account_id, expense_account_id, destination_account, beneficiary, payment_method, reference, payment_date, notes, version. version is the current VOUCHER version. Methods are Cash, Mobile Money, Bank Transfer, Cheque. Beneficiary is read-only from the item provider.
- Only database UUID item IDs are actionable. Reconciliation flags block payment. Partial disbursement stays on the payable list, not fully settled history.
- Unknown outcomes keep original inputs/key locked. Check saved payment calls the by-idempotency-key GET and refreshes the canonical voucher without posting again. Lost-response retries preserve the original voucher version too.
- Multi-item receipts are read by payment ID and rendered only from the confirmed payment record; they do not use aggregate PV PDF. Identity checks expect payment.id, payment.item_id, payment.voucher_id and receipt_number in the canonical record.
- UI explicitly describes recording a verified external payment, not initiating a transfer. Server permissions remain authoritative; no client actor/role is sent.
