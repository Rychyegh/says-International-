Frontend changes made against the reported contract
- Provider and voucher POST operations now persist random UUID retry keys and payload fingerprints in browser storage. Transport failure/409/503 keeps the original key across reload; changed unresolved payload is blocked, never silently retried with a new key. Storage failure prevents submission. Actor and endpoint scopes are separate.
- After a confirmed successful finance create, another explicit form submission may start a new operation with a new key, even with identical inputs. Student/admission retry behavior still replays completed operations as before. In-flight submissions share a request. Only keys/hashes/state are stored; no supplier details, voucher contents or credentials are stored by this helper.
- Draft form contents are not persisted by this change. After refresh the user must restore the same inputs to retry an unresolved operation. An unresolved operation with lost inputs requires database reconciliation, not clearing browser storage and resubmitting. This is a remaining UX limitation.
- payee_id, provider_id and providerId are accepted as provider aliases; conflicting IDs are rejected. Provider UUID is sent as payee_id.
- Quantity must be a positive whole number. Finite, non-negative amounts are required. A one-cent mismatch between quantity × unit cost and amount is rejected, not silently rewritten. Amount-only aggregate payloads use quantity1 and unit_cost=amount to preserve the total.
- Existing multi-item form explicitly uses aggregate quantity1 and total as unit cost. Academic period and line details stay in description; structured items are not claimed persisted by this backend set.
- Existing pre-audit then approve sequence remains; PRE_AUDITED is not payment authorization. Provider delete409 remains a visible error and keeps the record. No legacy /review or mixed-item approval API was introduced.
