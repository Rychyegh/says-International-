ACCOUNT PORTAL — BACKEND INTEGRATION, VERSION 2
Updated: 2026-10-14

DELIVERY STATUS
The frontend now has eight distinct accounting workspaces. Each section's tools remain visible if its API fails, rather than disappearing behind a common search/refresh screen. Local calculators and CSV preparation work without accounting data. Saving, posting, matching against a ledger, statement generation, and closing require the backend described here. No success or balance is invented when a request fails.

This repository does not contain the backend server implementation. The OpenAPI document specifies the required integration; it does not certify live endpoint availability.

WHAT EACH SECTION NOW DOES
1. Account Records: balanced journal editor, live debit/credit totals, draft revision, submission/approval/reversal, status-filtered journal register, account-specific general ledger with running balance, trial balance, CSV report exports.
2. Bank Reconciliation: account/date scope, signed bank CSV import, import validation, exact-reference match suggestions, manual one-to-one matching, posted ledger comparison, outstanding deposits/payments, live difference, persisted reconciliation working paper and approval history.
3. Balance Sheet: reporting-date preparation, classified assets/liabilities/equity, accounting-equation check, comparison with a saved statement, including accounts present only in the prior statement, CSV export, print/PDF, approval and immutable saved snapshots.
4. Tax & SSNIT Settings: separate VAT/levy and SSNIT tabs, rates effective on a chosen date, separate employee/employer configurations, effective-dated proposals/revisions/approval, version history, single-component inclusive/exclusive calculation, separate employee/employer contribution preview.
5. PV Receipts: released receipts only, PV/payee/reference/date/payment-method filters, confirmed-payment totals excluding voided receipts, receipt item preview, supporting/payment references, CSV register export, print/PDF. No voucher approval or disbursement controls.
6. Audit Trail: actor/action/resource/date/reference filters, event timeline, selected-event before/after field comparison, CSV export. Entirely read-only.
7. Account Setup: chart of accounts, account type/classification/parent, bank/mobile-money/cash directory, Head Admin creation and revision, account archive/reactivation with reason, opening-balance workflow linked to journals. Accountants can inspect configuration but cannot modify it.
8. Period Closing: period register, live server closing checks, links to sections with outstanding work, closure request, Head Admin lock/reopen, closure metadata, financial-period creation. Passing checks are never assumed from a blank checklist.

CONNECTION AND COMMON CONTRACT
Base URL: VITE_API_BASE_URL. Default: https://rcis-backend.onrender.com/api/v1.
All paths below are relative to /finance/accounting.
Authorization: existing Bearer login token; derive institution, actor and role from the verified session.
GET list: {"items":[...],"next_cursor":null}. Follow opaque cursor pagination. Return a consistent snapshot across pages and complete per-record detail. Frontend rejects a malformed list or repeated cursor. Never silently truncate the ledger.
GET report: {"report":{...}}. Four report routes are listed below. Reports are complete for the selected scope; reject oversized scopes with 422 and ask for a narrower period instead of truncating.
POST: {"record":{"id":"...","version":1,...}}. Include the complete updated record and authoritative status. A 2xx without record.id is not confirmation.
Dates: YYYY-MM-DD. Timestamps: ISO 8601 UTC. IDs: strings. Currency: GHS.
Use exact decimal arithmetic and two decimal places for money on the server. Rates allow four decimal places. Validate finite amounts and ranges independently of the browser.
Errors: {"detail":"Actionable explanation"}, optionally outstanding_checks. 400 invalid input; 401 unauthenticated; 403 permission denied; 404 missing; 409 stale version/state/idempotency conflict; 422 failed validation, reconciliation or closing checks.

SESSION VERIFICATION — 2026-10-14 CORRECTION
The observed HTTP 403 "Complete session verification before accessing this resource" is an authentication-state rejection, not a missing accounting endpoint or an empty ledger.
The frontend now gates both Admin and Accountant routes with GET /auth/me on fresh login and restoration before mounting finance data providers. It accepts only the role returned by the server and requires requiresSecondFactor:false. Local portal flags do not establish a verified session.
GET /auth/me must remain accessible to a valid provisional token and return {user:{id,role,...},requiresSecondFactor:boolean,pinSetupRequired:boolean}. If the accountant must verify a PIN, return requiresSecondFactor:true. Do not return false while the same token is rejected by finance middleware as unverified.
The shared verification UI uses the existing POST /auth/verify-admin-pin {pin} and enrollment POST /auth/admin-pin {pin,password}. Despite their legacy names, these routes must support the authenticated accountant identity when accountant verification is required by server policy. Never convert an accountant to an administrator. Return a replacement fully verified token, the same user ID/role, and requiresSecondFactor:false after successful verification; apply the verified state consistently to /finance/fees and /finance/accounting/*.
If accountant accounts should use password-only login, issue an appropriately verified accountant token during password login and have /auth/me report false. Do not remove finance middleware or let the browser mark a token verified itself.
For protected-resource rejections, prefer HTTP 403 {code:"SESSION_VERIFICATION_REQUIRED",detail:"Complete session verification before accessing this resource"}. SECOND_FACTOR_REQUIRED is also recognized. The frontend routes these errors back to verification and restores the selected section for the same user afterward. It does not automatically replay financial writes. Ordinary 403 permission denials must use a different code and remain access errors.
PIN errors: 401 invalid PIN; 409 enrollment needed; 429 lockout with Retry-After. Keep provisional /auth/me and PIN routes reachable without requiring the very verification they perform. Do not expose PINs/passwords or put them into local storage/audit snapshots.
Backend deployment is not available in this repository. If the legacy PIN endpoints reject accountant roles, backend support above is required; frontend tests cannot establish live endpoint compatibility.

ACCOUNT RECORDS / CHART OF ACCOUNTS
GET /accounts
POST /accounts (Head Admin)
Body: {code,name,type,classification,parent_id,channel,bank_name,payment_reference?,description}.
type: asset|liability|equity|income|expense.
classification: current|non_current|capital|retained_earnings|operating|other.
channel: bank|mobile_money|cash|other or empty. parent_id may be null.
Return status active, version, and masked_payment_reference (never return full account/merchant numbers in a list or audit event).
POST /accounts/{id}/revisions: same editable fields plus expected_version. payment_reference omitted means keep existing; a supplied value replaces it. Parent must be active, in the same institution, and form no cycle. Enforce classification/type compatibility. Do not change type or identity of an account with posted history without a controlled migration.
POST /accounts/{id}/actions: {action:archive|activate,reason,expected_version}.
Reject archive for nonzero balances, unresolved transactions, active tax settings, active child accounts or other posting dependencies. Archived accounts remain in historical reports. Opening balances are journals, never editable account totals.
Payment accounts must share canonical IDs with existing /finance/payment-accounts and all billing/PV payment routes.

GET /journals
POST /journals
Body: {date,description,kind,supporting_reference,lines:[{account_id,debit,credit}]}.
kind: income|expense|adjustment|opening_balance. Require >=2 valid lines, one positive side per line, equal debits/credits in cents, active accounts, support reference and open posting period.
POST /journals/{id}/revisions: draft body plus expected_version. Only draft/returned records can be edited.
POST /journals/{id}/actions: {action,reason,expected_version}.
Transitions: draft/returned -> submitted; submitted -> posted on Head Admin approve; submitted -> returned/rejected. reverse of a posted journal creates a linked opposite journal atomically and marks the original reversed. Return/reject/reverse require a reason.
Do not affect the ledger before approval. Approval and posting must commit atomically. Never delete or silently edit posted entries. Reports must account for both original and reversal entries exactly once.

GET /accounts/{id}/ledger?from=YYYY-MM-DD&to=YYYY-MM-DD
from optional; to required.
Report: {account_id,from,to,opening_balance,closing_balance,lines:[{id,date,reference,description,debit,credit,running_balance}]}.
Return posted entries in deterministic chronological order with opening balance before from. Use the account's documented normal-balance convention consistently for running balances. Validate account scope and date ordering. Zero entries is an authoritative empty report, not a request error.

GET /reports/trial-balance?as_of=YYYY-MM-DD
Report: {as_of,total_debit,total_credit,lines:[{account_code,account_name,debit,credit}]}.
Include all posted accounts, opening journals and reversals up to the date. Debit/credit balances and totals must reconcile; do not derive this from fee collections alone.

BANK RECONCILIATION
GET /accounts/{id}/transactions?from=YYYY-MM-DD&to=YYYY-MM-DD
Both dates required. Account must be bank/mobile_money/cash.
Report: {account_id,from,to,snapshot_id,closing_balance,lines:[{id,date,reference,description,amount,reconciled}]}.
Amount is signed from the payment-account perspective: incoming positive, outgoing negative. Include transaction IDs, not mutable display references. snapshot_id identifies the ledger state used for preparation.

GET /reconciliations
POST /reconciliations
Body: {account_id,from_date,as_of,statement_balance,outstanding_deposits,outstanding_payments,supporting_reference,notes,ledger_snapshot_id,statement_lines:[{line_id,date,reference,description,amount}],matches:[{statement_line_id,ledger_transaction_id}]}.
CSV stays in the browser until the user saves. The client accepts <=2 MB, 1..5,000 lines, quoted CSV, YYYY-MM-DD dates and nonzero signed amounts with <=2 decimals. The server must repeat validation, enforce the date scope, file-equivalent size limits and unique line_id values. All referenced accounts/transactions belong to the session institution.
Validate each match: IDs exist in the submitted lines and selected ledger snapshot; equal signed amounts; one-to-one; ledger entry not reconciled elsewhere. Reference matches are suggestions only; amount-only matches are not automatically selected.
Compute adjusted_statement_balance = statement_balance + outstanding_deposits - outstanding_payments; difference = ledger_balance - adjusted_statement_balance. Derive ledger_balance from the server, never from a client field.
Return the full working paper, reference, ledger_balance, adjusted_statement_balance, difference, status and version.
POST /reconciliations/{id}/actions: submit|approve|return|reject with expected_version; decisions require the corresponding role. Approval requires zero difference, no unexplained unmatched statement lines, substantiated outstanding items, valid support reference and an unchanged ledger snapshot. Mark matched ledger entries reconciled atomically on approval; detect simultaneous competing reconciliations. Drafts do not reserve or post ledger transactions. Returned drafts can be re-prepared while retaining history.

BALANCE SHEET
GET /statements
POST /statements body: {as_of,notes}.
Generate and persist a server ledger snapshot. Return {id,reference,as_of,status,version,prepared_by,approved_by?,ledger_snapshot_id,lines:[{account_code,account_name,type,classification,amount}]}.
Line type: asset|liability|equity. Classification reflects current/non-current items and capital/retained earnings as appropriate. Signed normal balances must include opening balances, accumulated surplus and current net income. No client-supplied balances are accepted.
POST /statements/{id}/actions: submit|approve|return|reject.
Approval requires assets = liabilities + equity and an unchanged ledger snapshot; approve -> approved. Reject stale statements with 409 and require a new draft. Approved statements remain immutable. Saved records must contain all lines because the UI compares snapshots without a separate detail fetch.

TAX AND SSNIT SETTINGS
GET /tax-settings
POST /tax-settings
Body: {name,category,rate,applies_to,effective_from,effective_to,account_id,reason}.
category: VAT|NHIL|GETFUND|SSNIT_EMPLOYEE|SSNIT_EMPLOYER|OTHER.
applies_to: payroll|taxable_purchases|taxable_sales. effective_to may be null.
POST /tax-settings/{id}/revisions: draft body plus expected_version, draft/returned only.
POST /tax-settings/{id}/actions: submit|approve|return|reject. Approval -> active.
Keep old approved versions and prevent overlapping active versions for the same category/scope. Validate employee/employer categories against payroll scope and appropriate posting account types. Snapshot rate/version, taxable base and calculated amount on each applicable posting. Past transactions are never recalculated merely because a rate changes.
The UI's calculator previews ONE tax/levy component, inclusive or exclusive. It is not a complete VAT-return engine or a declaration that school fees are taxable. The SSNIT preview separates employee deductions and employer contributions; it is not a statutory remittance split. No legal rate is hardcoded. Backend payroll/tax rules must determine applicability, pensionable base, contribution caps, tax/levy combinations, exemptions, remittance allocation and rounding from approved current rules.
These settings do not establish GRA e-invoice certification, file tax returns, or pay SSNIT automatically.

PV RECEIPTS (READ ONLY)
GET /receipts
Return only receipts released after PV approval and actual confirmed payment, including partial item payments as separate receipts. Approved but unpaid vouchers must not appear as receipts.
Whitelist fields: id,receipt_number,voucher_reference,payee,payment_date,amount,payment_method,payment_reference,items:[{description,amount}],supporting_reference,receipt_status,void_reason.
receipt_status: issued|voided; omitted legacy status displays as issued. Voided receipt values are excluded from confirmed-payment totals and marked on prints.
Never include private approval notes, bank credentials, pending-voucher detail, or approval/disbursement capabilities for Accounts. Store links to canonical voucher/item/payment IDs on the server. Publish the receipt projection from the existing payment transaction, not a separate manual receipt store. Retain void/reversal history.
This is a payment receipt, not a GRA-certified VAT invoice. Document export is a client print/save-PDF action.

AUDIT TRAIL (READ ONLY)
GET /audit-events
Fields: id,occurred_at,actor_name,action,resource,reference,reason,before,after.
Lists include field snapshots for the selected-event comparison. Append events for creation, revision, submit, approval, return/rejection, posting, reversal, rate activation, archive/activation, closing and reopening. Actor is session-derived; timestamps are server-generated.
Do not expose credentials, full payment-account identifiers, tokens or unrelated personal information in before/after snapshots. Events are append-only; provide no client update/delete route. UI filters loaded pages by actor/action/resource/date/reference and exports the filtered register. CSV export neutralizes formula-leading text.

PERIOD CLOSING
GET /periods
POST /periods (Head Admin): {name,start_date,end_date}.
Require valid non-overlapping date ranges. Initial status open.
Return closing metadata when available: closed_by,closed_at,carry_forward_reference,statement_reference.

GET /periods/{id}/checks
Report: {period_id,period_version,check_token,checked_at,ready_to_close,checks:[{key,label,status,message}]}.
Required check keys:
student_balances — outstanding balances reviewed and reconciled (not necessarily zero).
reconciliations — all required payment accounts reconciled.
journals — unresolved journals handled.
receipts — required supporting receipts present.
taxes — applicable tax/contribution liabilities reviewed.
statements — closing statements approved and current.
status: passed|failed|not_checked. Include actionable messages and any additional checks. UI requires all required checks present and all checks passed; a missing result is NOT a pass.
check_token binds institution, period ID, period version and financial-data snapshot; expire it after a short server-defined interval. Re-run/revalidate checks transactionally on actions so a stale token cannot bypass changes to the ledger.

POST /periods/{id}/actions: {action,reason,expected_version,check_token?}.
request_close: Accountant or Head Admin; open -> pending_close, requires current check_token.
close: Head Admin; pending_close -> closed, requires a newly valid check_token after the version changes. UI requires checks to be rerun before this approval.
reopen: Head Admin; closed -> open, reason required, no closing token required.
Close atomically locks all posting routes, including existing billing/PV routes, and carries forward balances once. Reject with 422 and outstanding_checks if unresolved. Record the carry-forward and closing statement references. Reopening/re-closing must not duplicate carry-forward postings.

RETRY AND CONCURRENCY RULES
All POST requests send Idempotency-Key. The client hashes actor/path/payload so identical retries after a timeout/reload use the same key. Store payload hash and result transactionally, scoped by institution, principal, method and path. Same key+payload returns original result; conflicting payload returns 409. Distinct genuine transactions need distinct supporting references when other input is identical.
All revisions/actions send expected_version; require exact equality and increment version. Server state-transition checks are mandatory even if the UI hides an action. Never create a journal/payment twice while approving or retrying a request.

ACCEPTANCE CHECKS
- All eight sections show distinct tools even when every accounting endpoint returns 503.
- Accountant cannot alter chart setup, approve journals/PVs, disburse payments, or close/reopen a period; direct forbidden API calls return 403.
- Invalid/unbalanced journals cannot post. Reversal and duplicate retries preserve an exact ledger.
- CSV import rejects invalid dates/amounts; duplicate ledger matches and opposite signs fail; approval detects stale snapshots/concurrent matching.
- Balance sheet balances and comparison retains prior-only accounts; stale statements cannot be approved.
- Tax history survives new rates; overlapping scopes and incorrect category/application combinations fail.
- Receipt projection excludes unpaid vouchers; voided receipts stay visible and are excluded from confirmed totals.
- Audit differences show only changed fields; exported text cannot execute as a spreadsheet formula.
- Closing is blocked for failed/missing/stale checks and all existing backdated posting endpoints respect period locks.
- Run staging integration before production. Frontend browser tests use mocked APIs and do not confirm a deployed backend.
